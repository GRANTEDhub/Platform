## Working discipline (how changes get made)
- **Gate:** scope → **wait for the user's explicit "go"** → build → **show the diff before committing** → the user merges. Applying a migration is **not** a go-signal.
- **Migrations are migration-first and the user applies them** to prod (service SQL). Never run prod migrations from here — write tools (`execute_sql`, `apply_migration`, `deploy_to_vercel`) are blocked at the session level. The sandbox now has **read-only** Supabase/Vercel MCP reach to prod (schema via `list_tables`, `list_migrations`, logs, advisors, deploy/build status) — use it for verification. Note the read path has **no `execute_sql`**, so no row-level SELECT; and Anthropic/LLM calls still can't run from here.
  - **Ledger (0044+):** every migration file ends with `insert into schema_migrations (version) values ('<stem>') on conflict do nothing;` inside a `begin; … commit;` wrapper, so applying = running the DDL **and** recording it atomically (an admin can't forget the insert — it's in the paste). A skipped migration is then visible, not silent: `select version, applied_at from schema_migrations order by version;` and diff against `ls supabase/migrations/` — any file missing from the result is unapplied. (Exception: statements that can't run in a transaction, e.g. `create index concurrently`, drop the wrapper and run the insert as the final standalone line.)
- **The user (or a teammate) merges PRs.** Don't merge.
- **Open PRs READY FOR REVIEW, not as drafts.** This overrides the remote-environment default, on the user's explicit instruction (2026-08-12) — he was clicking "Ready for review" on every PR by hand. It also fixes a real problem: the three review bots only fire when a PR leaves draft, so opening ready starts them ~10 minutes earlier, before the merge decision rather than after it. Still no self-merge, and still no `enable_pr_auto_merge` (hard-denied in `.claude/settings.json`).
- **CI green is necessary, not sufficient.** The real gate is a **preview-URL check** on the actual deploy. Client-facing / PDF / infra-plumbing changes get **look-before-merge** (show a real regenerated artifact). Sandbox renders are illustrative, never confirmation — verify on real `app.grantedco.com` (not `*.vercel.app`; hard-refresh for Cloudflare cache).
- **Production is live only when "Current," not "Ready."** A Vercel deploy tagged Production/Ready is NOT serving `app.grantedco.com` until it's the **Current** deployment. After any merge, confirm production actually advanced — Vercel Overview's Production card shows the merge commit, or `app.grantedco.com/api/version` == latest `main`. **Instant Rollback pins production and silently suspends auto-promotion for every later merge** — so if you ever roll back, clear it (promote current) the moment the forward-fix ships. (Incident: a jsdom hotfix rollback to PR #70 on 2026-07-07 stayed pinned ~3 days; merges built "Ready" but never went live.)
- **Fast-lane** (cosmetic, no deps, no server runtime): may skip scope/mock and just show the diff — still no self-merge.
- **A PR that changes locked architecture updates THIS FILE in the same PR.** Not afterwards, not in a follow-up. This file went 11 days and 195 commits stale (2026-08-01 → 08-12) while GrantBot — bricks 0–2, a new read route, a launcher, two restyles — landed without a single mention here, so a fresh session started blind to all of it. A daily Routine now audits the drift (see *Keeping this file current*), but the Routine is a safety net, not the mechanism.
- **The review bots need 7–16 minutes, and merging inside that window buries their findings** on an already-merged PR that nobody is subscribed to. Three bots run here — `Claude Code Review` and `Vercel Agent Review` as check runs, Codex as a PR review with inline comments — and they only fire when a PR leaves draft. On the night of 2026-08-11 they produced **twelve findings and all twelve were real**, including two defects inside the fixes written for the previous round. So: **verify every finding against the code, and never dismiss one because it is tagged "nit" or P2.** If a PR is merged before they report, go read the findings on the merged PR anyway and fix forward on a fresh branch. **The merge gate is `verify` (CI), not the review bots** (Shannon's call, 2026-08-27): `Claude Code Review` posts as a `neutral`/informational check and never blocks merge, so once `verify` is green the PR is mergeable — don't hold it waiting on the bots, and don't surface "bot still running" as if it gates. Handle their findings **fix-forward, capped at one round**: verify each against the code, push the real/small ones, and if a bot's findings stop converging (each fix draws a new or reshaped one), **stop and report what's left in one note** rather than looping fix→re-review→fix.

## Locked architecture
- **Grant alert** = LLM-enriched, Handlebars template → **Chromium (`@sparticuz/chromium`) PDF**, one letter page. Facts are deterministic (`lib/grants/format.ts` + schema); narrative is LLM (`lib/alerts/enrich.ts`), shape-validated with deterministic fallbacks.
- **Fonts** embedded as local `@font-face` data-URIs (no CDN link) — serverless Chromium has no gstatic egress.
- **Persistence (save-once):** `grant_alerts` table + private `grant-alerts` bucket. Generate once, reuse the saved draft for preview **and** send → **preview == sent**. `lib/alerts/store.ts`.
- **Single client send path** = "Send grant alert" (also records `decision='approved'` + fires the completion screen). The old plain-text Send is gone.
- **Prospect alerts:** same one-pager; **convert-and-send** promotes prospect → lead (`lib/prospects/convert.ts`, idempotent) then emails. The `/go/<token>` booking link is **minted at draft-render time (prospect-scoped)** and baked into the PDF as a clickable link — so preview == sent. No `decision='approved'` for prospects (would pollute client dashboards).
- **HTML sanitizing = `sanitize-html` (pure JS). NEVER `isomorphic-dompurify`/`jsdom`** — jsdom can't bundle into RSC/serverless and 500'd every grant page (incident, PR #72). `lib/sanitize/html.ts`.
- **Matcher occupancy is profile-free; `client_profile` only enriches narrative.** Occupancy (seat_ref + seated/NONE gate) runs on grant + rubric + raw client fields; `client_profile` feeds a separate, structurally-isolated `enrichMatchWithProfile` call (its tool schema has no occupancy fields, so it can't flip a seat) that grounds why-this-org/concept/draft-email only. A distilled profile fed to the scorer pushed it into strict itemized seat-matching that buried integrative-fit clients (regional multi-sector orgs) — three fixes failed before the split (incident, PR #138 closed → #140). The seat-stability `profile=on/off` `profileInvariant` flag guards it. `lib/grants/engine.ts`. **The invariant covers BOTH occupancy paths.** The code-side supporting-seat scoped judge (`clientContextForJudge`, `lib/grants/subseat-routing.ts`) is likewise profile-free — it flips `seat_ref`/`fit_score`, so it too decides on the SAME raw client fields (name, org type, location, service area, funding needs, rules/constraints), never `client_profile`. Feeding it the distilled profile made this occupancy re-check decide on a richer substrate than the main pass — the same #140 drift, on the second path (#413). Locked by a unit test asserting no `client_profile` value reaches the judge context.
- **Supporting-seat routing for prime-ineligible specialists (`MATCH_SUBSEAT_ROUTING_ENABLED`, default OFF).** The under-credit half of the occupancy bug: on a government-only grant a specialist that genuinely fills an enumerated SUPPORTING seat was disqualified on prime-entity-ineligibility alone (`seat_ref=NONE`, 0) instead of routed to that sub-seat — the profile builder enumerated the seat (e.g. a "community-based reentry nonprofit" seat describing PTF verbatim), but the occupancy step conflated "can't prime" with "no seat". `SUBSEAT_ROUTING_ADDENDUM` (a prompt block appended to `MATCHING_SYSTEM_PROMPT` only when the flag is on) instructs: before disqualifying a prime-ineligible client, check the enumerated supporting seats; if it genuinely fills one (name the `S{i}_{j}` id AND its function), route to `Sub`/`fit_score=2` with a named-or-typed prime note, not NONE/0. Scoped to genuine enumerated-seat occupancy — NOT "any nonprofit on any gov grant". **Flag OFF is byte-identical to today** (the ternary yields `""`, so the request body is unchanged) and is the instant kill-switch if the console floods with sub-fits. Gated behind a model-in-the-loop eval (`subseat-routing.eval.test.ts`, `RUN_SUBSEAT_EVAL`) that must show the miss set surfaces without regressing the hit set before the flag is flipped. **The addendum leads with a `DEFER FIRST` block** so it can't contradict the existing unconditional rules: it defers (follows the pre-existing rule, no routing) whenever the grant is SUPPRESSED for any reason (`suppressed` is never set false here), `subaward_prohibited=true` (Facilitator collapse wins), or the client is a for-profit / federal agency (HARD ROLE RULES win) — the routing applies ONLY to sub-capable entity types (nonprofits) on sub-permitting, non-suppressed grants. The eval carries a **carve-out band** proving each of those three deferrals actually fires (a DEFER-FIRST trigger applied to the miss base must NOT route to Sub, and a suppressed match must stay suppressed), and its hit-set zero-regression key includes exact fit + role + suppressed so a same-family score nudge or a silent suppression flip can't slip through. The eval must still be run (`RUN_SUBSEAT_EVAL=1` + creds) and pass before the flag is flipped. `lib/grants/engine.ts`.
- **Feedback → scoring calibration is a BOUNDED, DOWNWARD-ONLY post-model nudge, flag-gated (`MATCH_CALIBRATION_ENABLED`, ON (global)).** (The flag is a single global boolean — true for all clients, not per-client scoped.) `match_feedback` was write-only w.r.t. scoring; `lib/grants/calibration.ts` is the consumer that closes the loop — the automated replacement for the manual "staffer hand-writes `matching_rules`" bridge. It hooks in at the ONE seam between score-computed and card-written — `scoreGrantClientPair` (`pipeline.ts`, protected) calls `calibrateMatch(db, match, client.id, grantRow.focus_areas ?? [])` **immediately after `matchGrantToClient`, before the `qualifies` gate** (a ~3-line flag-gated hook: `const match` → `let match`, one call, one import — the ONLY protected-file change). All logic + tests live in the non-protected `calibration.ts`/`calibration.test.ts`. **Cold-start guarantee: flag OFF, or no relevant feedback, returns the engine score UNCHANGED** (identity, tested by reference) — so a client with no feedback yet scores exactly as today, and OFF does no DB read. **Relevance is the TIGHTEST launch scope (deliberately conservative, widen later): a past PASS counts only when it shares this grant's seat FAMILY (`seatFamily`: P\*→prime / S\*→supporting / else none) AND an overlapping focus area** — so a bad match in one category can never tug an unrelated one (cross-category bleed is the failure mode this guards). **A "pass" is a GENUINELY PASSED card (`decision='passed'` — a staff reject or a client Pass), NOT the direction-neutral score-Disagree control** (its caption is "what did it get wrong?", so a bare `agree=false` can't tell "too high" from "too low" — counting it would let a "should be higher" flag nudge future scores DOWN); attempt-referenced false-negative flags on suppressed matches (`decision` null) never count either. Agreements never offset; only passes are a signal. **Corpus hygiene (two filters before counting): `n` counts DISTINCT passed cards, not rows (`dedupeByTarget` on `review_card_id`/`match_attempt_id`) — the raw corpus double-counts because the reject-decision path and the score-Disagree control each write a row for one card, which would silently halve the ~K threshold; and a pass filed AFTER the grant's deadline is excluded (`isExpiredWhenPassed`) as a timing/cleanup pass, not a fit judgement.** (The deadline is read live today; a write-time snapshot is tracked in the #402 follow-up so a re-shred can't retroactively un-expire a pass. Both filters only ever DROP downward signals, never add — they fail toward not-suppressing.) **Each relevant pass is a UNIT negative signal (contribution clamped to `[-1, 0]`); a BARE pass — the shape ALL real feedback takes, since the Disagree/Pass control posts a reason but no `corrected_score` by design — counts as `-1`** (`BARE_PASS`; a soft `-0.5` never crossed the `round()` threshold, so bare passes could never move a score — the feature was inert against every row the product collects). **Math: shrinkage `w = n/(n+K)`, K=5, and with per-pass magnitude 1, `|s·w| = n/(n+K)` crosses 0.5 at n=K — so a single pass (and up to four) moves the integer score by NOTHING; ~5 consistent passes move it exactly one point; the move is hard-capped at ±1 and downward-only** (`deltaInt = -round(|max(s·w, -1)|)`, applied to the FRESH engine score each re-score → never compounds, never raises, never breaks the seat ceiling, floored at 0). A graded `corrected_score` (no UI submits one today) is clamped to the same `[-1,0]` band, so one harsh row can't move the score alone. Hard-gated matches (suppressed/disqualified) are never touched. **Explainable, never silent:** a move appends `Calibration: lowered N→M …` to `reasoning_context.fit_score_derivation`. **Per-client isolation is the `client_id` predicate in `loadClientFeedback`, NOT RLS** — the scoring path runs service-role (RLS bypassed), so the predicate is the boundary (locked in the test with a filtering fake DB). Index `match_feedback_client_idx` (migration 0083) serves the per-client score-time lookup (0013's `(grant_id, client_id)` is grant-leading).
- **Generic-over-specific demote is a CARD-SURFACING tag, NOT occupancy, flag-gated (`MATCH_GENERIC_NEXUS_GATE_ENABLED`, default OFF).** Fix #6: an org matches a grant's BROAD theme but lacks the SPECIFIC qualifying dimension it gates on (the canonical case — NWACC on a reentry-EDUCATION grant on "job training", no confirmed correctional-education history). The scorer already ADMITS the gap in its first-pass caveats ("inferred from mission alignment", "not confirmed as a current program area", "history in that specific context is unverified"). `lib/grants/generic-nexus.ts` is a scoped second model call (the #414 judge pattern) that re-reads those caveats and classifies the qualifying dimension as **`entailed_by_identity`** (the org's CONFIRMED identity performs this kind of work; the gap is execution — MOU / past-performance / SAM / budget → a legitimate execution-conditional 2, LEAVE) or **`inferred_from_adjacency`** (the dimension is inferred from thematic adjacency; the org may not do this specific work → demote + flag). The discriminator is **entailed-vs-inferred, NOT function-vs-artifact** — the latter over-fires because a legit "no existing BWC program" (Columbia County, a confirmed law-enforcement entity) and a real miss "no correctional programming" (NWACC) are both surface "no-confirmed-program" caveats. **Action is DEMOTE-WITHIN-2 + a lead `before_you_approve` flag, NOT suppress and NOT a fit 2→1 cap** (deliberately conservative for launch, widen later; unlike the circular-geo hard drop, an inferred nexus is sometimes a real-but-undocumented fit, so the card stays visible and console review catches it). Demote = a persisted `review_cards.generic_nexus_flagged` (migration 0084) sorted `ASC` right after `fit_score DESC` on all three card lists (review / grants / intel pages) — and ahead of `created_at DESC` on the review list, the only one carrying that tiebreak. **Two locked properties:** (1) **EXISTENCE test, not purity** — one inferred-nexus caveat flags the card regardless of how many execution caveats sit beside it (NWACC's one nexus caveat + four execution caveats → flagged); the applier keys on `basis` alone (`nexusFlagFromJudgment`). (2) **Errs toward SURFACING** — the prompt defaults to `entailed_by_identity` when genuinely ambiguous (the middle band: county→jail, SUD→justice-involved), and the fail-safe (missing / unparseable / thrown) returns NO flag; under-flagging a real match is the cheaper error. **Eval-hardened against boundary over-flagging** (first run: FLAG band passed every run; Arisa×MAT flagged 1/3, Faulkner×jail 2/3): (a) an **exhaustive execution non-trigger list** — past-performance, MOU, SAM, budget, licensure, key-personnel, and a **sub-capability within a confirmed function** (buprenorphine-prescribing for a confirmed SUD provider) — can NEVER trip the flag no matter the "inferred/unconfirmed" wording (what is unconfirmed decides it: an execution attribute → entailed; the qualifying function/population itself → inferred); (b) a **structural-entailment** default (an entity-type-typical function — county→jail, sheriff→policing — is entailed even when the instance is "assumed / not confirmed"); (c) a **concreteness guard** — an inferred verdict must QUOTE the nexus caveat (`triggering_caveat`) or `nexusFlagFromJudgment` drops it to no-flag, the code-side anti-leak that also robustifies against run-to-run occupancy/seat variation feeding the classifier different caveats (it anchors on org identity + a quotable function/population caveat, not the unstable seat). **Profile-free by construction** — the classifier reads the SAME raw client fields the occupancy pass uses (`clientContextForJudge`), NEVER `client_profile` (the distilled narrative would undermine the "confirmed identity" anchor). **NOT occupancy → hooks at the card-surfacing seam in `pipeline.ts` (protected) alongside `calibrateMatch`, engine.ts UNTOUCHED (0 diff)**: after `enrichMatchWithProfile`, `evaluateGenericNexus(match, client, grantRow)` reads the first-pass occupancy caveats on `match` (not the enriched narrative), prepends the flag to `enriched.before_you_approve`, and threads `generic_nexus_flagged` into the card insert/update. **Flag OFF is byte-identical** (guard short-circuits before any model call; column written `false` = default = today's sort position; added `ORDER BY` inert while all-false). Prospect cards are never flagged in v1 (the classifier hooks the client-match path only). Deterministic plumbing tests in `generic-nexus.test.ts`; the classification quality is gated by a model-in-the-loop eval (`generic-nexus.eval.test.ts`, `RUN_GENERIC_NEXUS_EVAL`) that must pass before the flag is flipped, with a bar set to what the classifier can RELIABLY do. **Three eval rounds proved the two Arisa-SUD fixtures (`Arisa×MAT` vs `Arisa×justice-involved-SUD`) are the SAME org on opposite sides of a razor-thin boundary the model flickers ~1/3 on in BOTH directions — and no prompt/vote makes a genuinely-ambiguous case deterministic**, so the gate stops demanding it. FOUR bands: **KEEP** (the CLEAR execution-only keeps — `Columbia-BWC` / `Faulkner-BWC`) is STRICT, 0 flags every run (the one true defect — over-demoting a CLEAR match — stays locked); **FLAG** (the CLEAR nexus gaps — `NWACC×reentry` / `Arisa×dementia`) flags in the MAJORITY of runs; **MIDDLE** (`Faulkner×jail`) leans entailed (majority not-flagged); and an **AMBIGUOUS** band (`Arisa×MAT` / `Arisa×Family-SUD`) asserts ONLY that they stay surfaced conditional-2s — flag DIRECTION deliberately unasserted, because the feature is **DEMOTE-ONLY by type** (`NexusFlag` is `{flagged, note}` — no field for a suppress or a score change; the hook never writes `suppressed`/`disqualified`/`fit_score`, and `qualifies` is computed before it runs), so either outcome on an ambiguous fixture is a harmless sink-one-slot-with-a-note, never a suppress. Majority, not unanimity: an ambiguous flicker is the cheap-error direction by design, and the strict KEEP band preserves the only guard that matters. (`expect.soft` so every fixture in a band reports.)
- **Low-award-count gate is a CLIENT-CONDITIONAL pre-filter skip, flag-gated (`MATCH_LOW_AWARD_GATE_ENABLED`, default OFF).** A grant expecting FEWER THAN 10 awards is a hard-skip (suppressed, not surfaced) for a client UNLESS the client's `org_type` is `state_government` or `higher_education` — state agencies and universities realistically compete for low-award national programs; `local_government` (counties/cities), `nonprofit`, and `small_business` mostly cannot, and those programs only clutter their reports. Logic lives in the non-protected `lib/grants/award-count-gate.ts` (`lowAwardSkipReason(extracted, client)`); **the ONLY protected-file change is a one-line hook in `jsPreFilter` (`engine.ts`) AFTER `grantLevelSuppressionReason`** — so the pre-existing grant-level cuts (single national award, TTA ≤10 slots) still run FIRST and still kill for EVERYONE. This ADDS a per-client <10 gate, it does not replace them, so the carve-out only ever rescues the **2–9 award band** (a 1-award national / TTA ≤10 stays killed for state-gov/IHE too — correct: those go to national intermediaries / need multi-state infrastructure no AR-anchored applicant has). **Client-conditional by necessity:** the same grant must skip for a county but survive for a state-gov/IHE client, so the check needs `org_type` at gate time, which only the per-client `jsPreFilter` seam has. **FAIL OPEN on every missing input:** a skip requires a REAL integer count `< 10` AND a KNOWN, non-carve-out `org_type`; a null/empty/non-numeric count, or a null/empty/legacy-unrecognized `org_type`, surfaces (mirrors `grantLevelSuppressionReason`'s `|| "999"` convention — `num_awards` is frequently empty, the Simpler API omits it). **Not silent:** the skip flows through `jsPreFilter` → `scoreGrantClientPair` records a `match_attempts` row (`outcome='prefiltered'`, `prefilter_reason`), queryable per (grant, client) — unlike the grant-level pre-shred `skip_reason`. **Flag OFF is byte-identical** (returns null before any effect) — the instant kill-switch. Deterministic (no model call) → fully covered by `award-count-gate.test.ts`; no model-in-the-loop eval needed to flip the flag. Forward-only: runs at match time, never rewrites existing stored cards. `lib/grants/award-count-gate.ts`.
- **IntellEngine QA / Intel is the ON-DEMAND, staff-triggered verification pass (`lib/grants/intel-review.ts`, migration 0086, NO flag).** A second look at a card that already SURFACED: Opus 5 + a bounded one-tool web-fetch loop (reuses GrantBot's `runToolLoop` + the `.gov`-allowlisted `fetchGrantSource`) re-checks the engine's fit score / eligibility against the AUTHORITATIVE source and writes a verdict into the STAFF-ONLY `card_intel_reviews` table (migration 0086). **TWO ERROR CLASSES it scores** (`INTEL_SYSTEM_PROMPT`): (1) the ALLOCATION error — for formula/allocation programs entity-type eligibility ≠ application eligibility (a disparate/'asterisk' jurisdiction or a subgrantee that can't prime; corrected factor `eligibility`/`seat_role`); (2) the PURPOSE-FIT mismatch (Item 1, the NWACC audit) — the client is entity-eligible but does NOT perform the funded ACTIVITY / serve the funded POPULATION (an eligible IHE on a museum-workforce program with no museum, or on a national library-RESEARCH program while its library does routine local service; corrected factor `mission`/`program_history`). The purpose-fit class is **CATEGORICAL, not competitive** — it demotes ONLY when the org does not do the funded work AT ALL (a broad asset like "has a library" is NOT "does the funded work"), NEVER on entity-eligibility alone and NEVER on "weaker competitor" fit (a genuine performer that is a smaller applicant is AFFIRMED). It grounds exactly like the allocation error (FETCH the NOFO, read the funded purpose there — never from memory) and rides the SAME apply + fail-safe path, so under broad apply a grounded+refute-clean purpose-fit demote auto-applies platform-wide (the eval's affirm controls are the over-demote backstop). **APPLIES its verdict now (PR E), but still never re-scores:** the sibling `/api/review/[id]/intel` route writes the raw verdict to `card_intel_reviews` AND — when `AUTO_INTEL_APPLY` is on — projects it onto the card's `qa_*` OVERRIDE columns through the SAME `buildQaPatch`/`applyQaPatch` the drain uses (one apply path, no drift). It still never touches the engine's own `review_cards.fit_score` / seat / decision / suppressed (it never calls `scoreGrantClientPair` — it doesn't re-score): the DISPLAYED score becomes QA's via the read-layer coalesce, the engine's matcher record is preserved, and there is no suppress column, so a demote only lowers the number and never removes a card. Two differences from the JAG-only auto sweep: it applies for ANY CFDA (the human clicking Re-run is the fan-out gate) and stamps `qa_reviewed_by` with the acting staff id; the auto path's `created_by IS NULL` gate is UNTOUCHED (this route applies its OWN verdict directly rather than leaning on the drain, which deliberately skips human verdicts — but it RE-READS the persisted `card_intel_reviews` row before projecting (PR G), so a concurrent Re-run on the same card can't leave `review_cards` reflecting a superseded verdict). Same master flag — `AUTO_INTEL_APPLY` OFF disables ALL card rewrites, auto and manual alike. The apply-write is non-fatal (the verdict is durably saved even if the projection fails; the response returns `applied`). The card keeps the engine's score; the verdict says "engine 3 → QA 1, here's why"; a human passes/forwards. **FAIL-SAFE — GROUNDING is the gate, the refute is ADVISORY (PR F):** an adverse verdict (demote/flag) is RETAINED only when it is GROUNDED — the pass actually FETCHED a relevant `.gov` page (`hasSuccessfulFetch`; `fetchGrantSource` is `.gov`-allowlisted and only fetches this grant's sources, so an ok fetch is a real authoritative read). The adversarial refute (`realRefute`, a bounded skeptical second read) still RUNS and is RECORDED as an advisory note (`refute_survived` true/false/null) but NO LONGER vetoes the verdict — a redundant veto also killed CORRECT grounded demotes (the live MS County incident: a right JAG demote overturned by an over-eager second read), and a grounded demote is never-hide + sourced + one-click-revertible, so it was dropped. An `affirm` with no successful fetch is likewise downgraded. Grounding — a real fetched `.gov` page, not any quote or URL the model emits — is the gate; the model call is also RETRIED when it returns a verdict-less structuring result, so a one-off structuring miss no longer silently becomes "no usable verdict": two earlier gates (a verbatim-substring `quoteGroundedInBodies`, then a host-match on the model's cited `source_url`) each suppressed correct, fetched, refute-confirmable demotes because the phase-2 model reliably omits a clean quote / the URL (the JAG case, three eval runs); grounding is now "a real `.gov` page was fetched for the refute to read." Any shortfall (ungrounded, genuinely refuted, or the refute couldn't complete) → `unverified` in code (`finalizeIntel`); fetch-only has no search, so a source it can't reach → typed "could not retrieve" → `unverified`, never a guess. A refute that can't complete (threw / no budget) stores `refute_survived=null` (a retry signal), distinct from a genuine refutation (`false`). Because it never writes `fit_score`, a flaky fetch or a misread can't move a score. QA also returns corrected `qa_factor_scores` (same shape as `factor_scores`) + a `confidence` (recorded, NOT the apply gate — grounding + refute is) so a later applied demote keeps the card's factor bars consistent with the number. **STAFF-ONLY / NEVER client-facing, at the RLS layer:** RLS is ROW-level and 0055's `review_select` exposes a client member's own `review_cards` rows (every column), so the raw QA voice can't live in a review_cards column — it lives in `card_intel_reviews`, whose SELECT policy is `public.is_staff()` ALONE (no client-member policy, all writes service-role, the 0080 grantbot pattern). It renders only through the console's default-null `intel` slot (the portal never passes it), never in `before_you_approve` or any client surface. **PROFILE-FREE** (`clientContextForJudge`, the #140 discipline). Fetch-only can't discover a separate allocation page, so a CFDA → authoritative-`.gov` seed map (`lib/grants/allocation-sources.ts`; JAG 16.738 → the BJA allocation page) hands the reviewer the right page. This is the "prove it on-demand first" half; the AUTO-inline promotion (an enqueue hook in the protected `pipeline.ts`, a QA drain + watchdog, a card lifecycle status, cost monitoring) is a separate LATER build with the protected touch. - **No `router.refresh()` anywhere in the chat.** Thread ordering lives server-side; refreshing the route to pick it up re-renders the entire client dashboard under the panel on every message. Refetch from the read route instead.
- **Per client by mount point, and the conversation guards prove it.** `clientId` is a prop from the page; both routes re-check that a conversation belongs to it and 0080 keys both tables on `client_id`. The launcher is mounted **outside `ClientDashboard`** on purpose — that component is the actor-aware hub the client portal will mount too (Phase 2), and the pack carries staff notes.
- **`BLANK_CONVERSATION` ("new") is a real state, distinct from absent.** Absent `?c` means "no preference, open the most recent thread"; the sentinel means "a started-but-unsent conversation with no id yet". Conflating them sent expand/collapse into the *previous* thread. `lib/grantbot/wire.ts` owns the token plus the one wire mapper both surfaces use.
- **A send belongs to the transcript it was asked in.** `send()` captures an epoch; `loadThread`/`newConversation` bump it, and every UI write checks it — otherwise a reply lands in whatever thread the reader switched to mid-turn. Same shape for the paste attachment: only clear it if the composer still holds what that turn consumed.
- **Chat surfaces own their scroll.** The full page is `h-full` + `overflow-hidden` with `shrink-0` bands; rail and transcript each carry their **own** `overflow-y-auto`; the composer is a `shrink-0` sibling, pinned structurally rather than with `position: fixed`. **`min-h-0` is load-bearing** on every flex ancestor — a flex child's default `min-height: auto` refuses to shrink below its content, which silently hands the scroll back to the document and restores the original bug (composer scrolling out of view). This works **without touching `app/(app)/layout.tsx`**, which already gives `<main>` a definite height.

### GrantBot document artifacts (Brick 1a; migration 0082, `GRANTBOT_ARTIFACTS_ENABLED`)
- **GrantBot's first WRITE capability, and the read-only invariant now has a SECOND flag.** Two staff-only, append-only tools — `create_artifact` / `edit_artifact` — let GrantBot draft an HTML document deliverable per client and revise it over sessions. Held to the **same discipline as web-fetch**: tool set is a **server-side constant assembled in `turn.ts` from the flags, never from the request body**; **`GRANTBOT_ARTIFACTS_ENABLED` defaults OFF and off is byte-identical to today** (no tools attached, instruction block appended *after* the cache breakpoint, `toolMode` "off" → no `tools`/`tool_choice` keys). The write reaches **only our own Postgres + private bucket** (no external egress — smaller surface than web-fetch's outward read), staff-only, never client-visible, never auto-sent.
- **The turn loop is now TOOL-AGNOSTIC.** `runFetchLoop` (single-tool, welded to web-fetch) became **`runToolLoop` in `lib/grantbot/tool-loop.ts`** — a server-assembled tool set + a **name-dispatched** closure (`turn.ts` routes `fetch_grant_source`→web-fetch, `create_artifact`/`edit_artifact`→artifacts). `web-fetch.ts` keeps only the fetch tool + framing. The byte-identical-off property is **re-proven under the generic loop** (`tool-loop.test.ts`), and holds for **both flags independently** (all-flags-off → one call, `toolMode` "off"). Don't reintroduce a tool-specific loop; add a tool by extending the server-side set + dispatch, not by forking the loop.
- **Versioned, append-only, roll-forward.** `grantbot_artifacts` (one per document, `client_id` cascade / `origin_conversation_id` set-null so it outlives the thread) + `grantbot_artifact_versions` (a full HTML snapshot per edit; **HTML inline**, KB-scale, one-query preview). **Rollback is a forward write** cloning an old version, never a destructive revert (same discipline as the transcript). Staff SELECT only, **no write policy** → all writes service-role (`lib/grantbot/artifacts-store.ts`). The private `grantbot-artifacts` bucket holds **rendered exports only** (PDF/.docx are Brick 1b), regenerable; no `storage.objects` policy (service-role signed URLs, 0075's pattern).
- **The artifact link rides the existing non-text-block mechanism.** A turn that writes a document appends a `{type:"artifact_ref", …}` block to the assistant message `content` jsonb — **exactly the `web_fetch_audit` mechanism**: `normalizeContent` drops it on read, so render/replay are unchanged and an artifact-free turn is byte-identical. **No change to `grantbot_messages`.**
- **Preview = a DOCUMENT-grade sanitize profile on the LOCKED `sanitize-html` engine.** The existing `RICH` profile (inline snippets) strips headings/tables, so `lib/sanitize/html.ts` gained **`sanitizeDocument` / a `DOCUMENT` profile** — a wider whitelist (headings, tables, lists, blockquotes, links) that still discards `style`/`<style>`/`script`/`img`. **Still `sanitize-html`, never jsdom/dompurify.** HTML is sanitised **on write** (the tool handler) *and* on read (the route), so `dangerouslySetInnerHTML` in the pane only ever sees whitelisted markup. **Plain, not house-styled** — brand fidelity is the future "Brander" build, deliberately out of 1a. Preview and the HTML export share one stylesheet (`lib/grantbot/artifact-html.ts`) so the in-panel view matches the download.

The pane **refetches from the read route** (`GET /api/grantbot/artifacts`) on a `reloadKey` the chat bumps via `onTurnComplete` — **never `router.refresh()`** (the locked rule). The corner launcher is unchanged in 1a. **The pane DEFAULTS CLOSED** (chat is what staff open the page for): closed, it collapses to a slim right-edge "Documents" tab and the transcript takes the full width; a click opens the two-column split, and the pane header carries a close control. `reloadKey` still bumps while it is closed — harmless, the panel is unmounted — and the panel fetches fresh on the mount that reopening triggers, so reopening is never stale. Flag OFF is still byte-identical (no wrapper, no tab).

### GrantBot artifact exports — PDF + Word (Brick 1b; `GRANTBOT_ARTIFACTS_ENABLED`, no migration)
- **Two RENDERED formats join the 1a HTML download, on ONE cache-keyed scaffold.** `lib/grantbot/artifact-export.ts` is the single path both formats flow through (`exportArtifact` → fetch versioned HTML → cache-check → render-on-miss → signed URL), so PDF and .docx don't duplicate storage/signing plumbing. The two renderers are **pure functions of the sanitised, versioned HTML** in `lib/grantbot/artifact-render.ts`. The 1a `.html` download stays inline-from-the-row (`../html` route) and never touches the scaffold — only the rendered formats need caching.
- **PDF reuses the LOCKED Chromium launcher AND its embedded fonts — no second browser stack, no CDN font link.** `renderArtifactPdf` calls `launchAlertBrowser()` from `lib/alerts/render.ts` (the same `@sparticuz/chromium` binary the grant alert uses) and is a thin `setContent → page.pdf()`. It **drops the alert's `pageRanges:"1"` clamp** (that pin exists because the alert is one fixed letter page; a concept proposal is multi-page) and takes its geometry from a print stylesheet (`artifactPrintHtml`: `@page` letter, ~0.9in margins, `break-inside:avoid` on tables/blockquotes/pre) via `preferCSSPageSize`. **It embeds the alert's vendored faces via the now-exported `loadFontCss`** (Source Serif 4 + Inter Tight as `@font-face` data-URIs) and leads the print `font-family` stacks with them — because this HTML renders in serverless Chromium, which has no gstatic egress and none of `ARTIFACT_DOCUMENT_CSS`'s named system fonts installed, so without embedding the PDF renders substitutes or tofu (the locked "fonts embedded as local @font-face data-URIs" invariant). The on-screen preview / `.html` download stay on the neutral system stacks — those render on the *user's* browser, so a typeface difference between the plain preview and the embedded-font PDF is the accepted trade-off vs. bloating the download with base64 fonts.
- **Word is a GENUINE `.docx`, not an .html renamed.** `renderArtifactDocx` runs `html-to-docx` (**the sole new dependency, approved**) over the sanitised body → real OOXML; the library maps `h1-h6`/`p`/`ul`/`table`/`strong`/`blockquote` to native Word styles. **The only net-new vuln in that dep's tree is `image-size` (a DoS in ICNS/JXL/HEIF parsers) and it is UNREACHABLE**: the DOCUMENT sanitizer strips `<img>` before any HTML reaches the renderer, so there are no images to parse. (`js-yaml`/`next` advisories predate 1b.) `html-to-docx` ships no types → minimal ambient decl in `types/html-to-docx.d.ts`.
- **Cache = pure function of `(artifact, version, format)`; invalidation is automatic.** Rendered exports live in the private `grantbot-artifacts` bucket (created empty in 0082) under `exports/<artifactId>/v<version>/<format>`. **Version in the key means a new version is a new object** — an edit produces v(n+1), whose exports simply miss the cache and render fresh, while v(n)'s objects are never served again. No explicit purge, no stale render; a cache HIT skips rendering and just re-signs. Served via a **short-lived signed URL** (`signedUrl(..., { download })` for a proper filename); the route 302s to it — same one-click UX as the 1a HTML `<a>`.
- **Flag-gated at BOTH ends, unlike the 1a reads.** The export route (`/api/grantbot/artifacts/[id]/export?format=pdf|docx`) 404s when `GRANTBOT_ARTIFACTS_ENABLED` is off, and the panel only shows the PDF/Word links inside the already-flag-gated pane — because these formats are *rendered* (Chromium + html-to-docx), not the "nothing exists when off, so the read is harmless" case the 1a list/HTML reads are. Staff-only (`getProfile`), node runtime, 60s budget (the alert routes' convention). **No schema change** — the bucket and tables are all from 0082.

### GrantBot cross-thread reads (`GRANTBOT_CROSS_THREAD_ENABLED`, default OFF; no migration, no protected touch)
- **Two READ-ONLY tools let GrantBot reach the client's OTHER threads on demand — `list_client_conversations` / `read_client_conversation` (`lib/grantbot/cross-thread.ts`).** A turn's context is ONE conversation; when a staffer asks about an earlier thread ("what did we decide last week", "the other JAG thread"), the answer lives in a sibling conversation the turn never loaded. `list` returns this client's recent thread rail (title + id + date, current thread excluded); `read` pulls one thread's transcript by id. **NO search infra** (the scope call) — the model picks the thread from the titles the way a staffer scanning the rail would; no embedding index, no ranked search.
- **The CROSS-CLIENT boundary is a CODE-SIDE `clientId` guard, NOT RLS.** The turn route runs on the SERVICE-ROLE client (RLS bypassed), and `grantbot_conversations`' SELECT policy is `is_staff()` (a staffer can read every client's threads), so RLS is not the per-client boundary here — the `clientId` predicate in `executeCrossThreadTool` is (the #140 discipline: on a service-role path the predicate is the boundary). `list` filters on `clientId`; `read` calls `getConversation` and refuses any thread whose `clientId ≠ ctx.clientId` — and a **cross-client thread and a non-existent one are refused with the IDENTICAL message**, so the tool never returns another client's content and never even confirms such a thread exists. Locked by `cross-thread.test.ts` (a `c2` thread is refused, its body never appears, and the refusal is byte-equal to the not-found refusal). A sibling thread of the SAME client discloses nothing new — that client's whole pack is already in the turn's context.
- **Read-only → the append-only transcript is untouched.** These tools only SELECT; no write path, so 0080's "what the transcript says GrantBot said is what GrantBot said" holds. Which threads a turn listed/read is stored as a NON-TEXT `cross_thread_audit` block on the assistant message (the `web_fetch_audit`/`artifact_ref` mechanism; `normalizeContent` drops it on read), so it's inspectable and byte-identical when empty.
- **Same three-way narrowing + byte-identical OFF as web-fetch/artifacts.** Tool set is a server-side constant assembled in `turn.ts` from the flag (never the request body); the instruction block is `cacheable:false`, appended AFTER the cache breakpoint and ONLY when on (so the flag-off system prompt is unchanged and existing caches aren't busted); with the flag off `toolMode` is "off" and neither `tools` nor `tool_choice` is added — the request, prompt, and stored row are exactly the pre-cross-thread ones. A read transcript is capped (`MAX_TRANSCRIPT_CHARS`, whole messages kept from the most recent backward so a long thread surfaces its conclusion) so one big thread can't push the next call past the context window. Staff-only (the turn route's `getProfile`). `lib/grantbot/cross-thread.ts`.

## Cron cadence & pipeline reality (prod, verified 2026-07-21)
- **Cron cadence.** Matching is decoupled from ingest. `/api/cron/ingest` runs twice daily (01:00, 08:00 UTC — new-grant fetch only). `/api/cron/match` and `/api/cron/client-match` run every 10 min (the drain + client-matching). `/api/cron/watchdog` runs every 15 min. `/api/cron/usaspending-refresh` runs monthly. Verified from Vercel cron config + prod logs 2026-07-21.
- **`status='error'` = the stale-opportunity-id 404 family** (not timeouts). Simpler.gov returns HTTP 404 when a stored opportunity id has gone dead (often after the forecast→active flip). These are `match_retry_count=0`, frequently `fon`/`funder` null (404'd on first fetch, never populated). They are **NOT matching timeouts** — do not re-chase the retracted "300s timeout / stuck grants" thesis (see `docs/research/2026-07-fr-and-ingest-reliability.md`). Recovery is a `source_url` re-point to the live id, but husks with no `fon` carry nothing worth recovering and are left parked per forward-fix-first.
- **Roster matching is chunked (Move 2, migration 0054).** `runMatching` no longer scores the whole roster in one 300s window — it scores within a wall-clock deadline and re-queues the remainder, resuming across drain cycles. Resume is cursor-free (attempts diffed since `grants.match_episode_started_at`, the per-episode marker); `complete` is set **only once the whole roster is scored**, so a grant can no longer time out at any roster size. Chunking only partitions *which* clients an invocation scores — the per-pair scorer (`scoreGrantClientPair`/`matchGrantToClient`) is untouched, so seats are invariant to the chunk boundary.
- **`clients.match_active` is the reversible per-client matching PAUSE (migration 0091, Lever A).** A real-but-not-yet-onboarded client should not have every new grant scored against it (token + QA spend) or pile alerts into the staff queue. `match_active boolean NOT NULL DEFAULT true` — `NOT NULL DEFAULT true` is load-bearing because the gate is `.eq("match_active", true)`, so a NULL would read as not-true and silently pause a client; defaulting true means applying the migration ahead of the code is a no-op until a client is flipped false by hand (SQL: `update clients set match_active=false where id in (…)`). **The forward gate is a ONE-LINER the maintainer applies BY HAND to the protected roster load in `runMatching` (`lib/grants/pipeline.ts`) — it is deliberately NOT in the feature PR, because additive features must not touch protected files: append `.eq("match_active", true)` to `db.from("clients").select("*").or(NON_LEAD_OR_FILTER)`. So a grep of `pipeline.ts` may not show it — the column + poller/drain skip + view-filter ship in the PR; the roster gate is the separate protected paste, and until that line is live the matcher still scores paused clients.** It is **forward-only**: `runMatching` fires per grant-enqueue, so un-pausing never re-scores the existing corpus — it only lets NEW grants match the client again (the deliberate NON-re-surfacing choice; re-surfacing existing matches on un-pause is a separate, unbuilt lever). **Pausing NEVER mutates or deletes a card** — existing alerts persist, just filtered. Two more skips, both non-protected: the intel QA machinery drops paused clients (flag-independent — the poller `pollAndEnqueue` stops NEW enqueues, and the drain `processOne` rechecks `match_active === false` at claim time so a job queued BEFORE the pause is skipped with no model call/cost), and the staff Review Queue (`app/(app)/review/page.tsx`) hides paused clients' cards by default with a text "Show paused (N)" toggle (staff-only; the client portal is a separate per-client tree, unaffected). The drain (`drainClientMatchQueue`) and the manual Add-to-Client / `/rematch` paths are deliberately NOT gated. `lib/report/paused-filter.ts` holds the pure view-filter predicate.
